    🚀 Day 13/90 – Revisiting Search vs Filter in Backend Development

    Today's revision wasn't about learning new Python syntax—it was about strengthening the way backend applications work with data.

    A search and a filter may look similar, but they solve different problems.

    A search looks for one specific record.

    A filter returns every record that matches a business rule.

    For example, filtering candidates based on minimum experience:

    minimum_experience = int(input("Enter minimum experience: ")) for candidate in candidates: if candidate["experience"] >= minimum_experience: print(candidate["name"])

    Another small concept I revisited today was using a Boolean variable to keep track of the program's state.

    found = False

    As soon as a matching candidate is found:

    found = True

    This simple pattern appears in many real backend systems—from authentication and payment processing to candidate search and validation.

    One takeaway from today's revision:

    Good backend code isn't about writing complicated logic. It's about combining a few simple programming patterns to solve business problems.

    🚀 Day 12/90 – Revisiting Search Logic and State Management in Python

    Today's revision was around a simple backend feature that appears in almost every business application—searching data.

    When we have a collection of candidates, searching isn't about jumping directly to the result. The application checks each candidate until it finds a match.

    target_name = input("Enter candidate name: ")

    for candidate in candidates:
    if candidate["name"] == target_name:
    print(candidate)

    While revisiting this, I came across another concept that's easy to overlook but used everywhere in backend development—state management.

    found = False

    At first, this variable simply means:

    "I haven't found the candidate yet."

    As the program checks each candidate, that state changes only when a match is found.

    found = True

    After the search is complete, the application can confidently decide whether to return the candidate or display a "Candidate not found" message.

    This same pattern appears far beyond search functionality:

    User authentication (logged_in)
    Payment processing (payment_success)
    Duplicate record detection (duplicate_found)
    Email validation (email_exists)

    Different business problems, but the same engineering principle.

    One thing I enjoy about revisiting fundamentals is realizing that many production systems aren't built using complicated logic—they're built by combining simple patterns in the right way.

    Every revision strengthens the foundation for writing cleaner backend code.

    🚀Day 11/90 – Revisiting Data Modeling and Collections in Python

    One of the concepts I revisited today was how backend applications move from handling one object to handling many objects.

    A single candidate is naturally represented as a dictionary:

    candidate = {
    "name": "Vaibhav",
    "experience": 5
    }

    But recruitment systems don't process just one candidate—they process hundreds or thousands. That's where a list of dictionaries becomes the right data structure.

    candidates = []

    candidate = get_candidate()
    candidates.append(candidate)

    The interesting lesson today wasn't just using append().

    It was understanding why it exists.

    I initially experimented with using += and discovered that dictionaries are iterable over their keys, which meant only the keys were being added to the list instead of the entire candidate object.

    That small debugging exercise reinforced an important idea:

    Use append() when adding one complete object to a collection.

    These are the kinds of fundamentals that seem simple, but they appear repeatedly in backend development—whether you're collecting API requests, processing resumes, or building an applicant tracking system.

    ML Revision

    Today's revision was Recall.

    While Precision measures how accurate the shortlisted candidates are, Recall measures how many of the truly qualified candidates the model successfully identifies. For AI-powered recruitment systems, both metrics matter because missing a strong candidate can be just as costly as shortlisting a weak one.

    Every revision session strengthens the foundation for building more reliable backend systems.

    🚀 Engineering Journal | Day 10/90

    One thing I've been consciously doing recently is revisiting Python fundamentals—not because I don't use them, but because I want to write cleaner and more maintainable backend code.

    Today's focus was on designing a single candidate entity.

    Instead of scattering candidate information across multiple variables throughout the program, I grouped everything into one structured dictionary and returned it from a dedicated function.

    def get_candidate():
    candidate = {
    "name": input("Enter candidate name: "),
    "email": input("Enter candidate email: "),
    "location": input("Enter candidate location: "),
    "mobile_number": input("Enter mobile number: "),
    "experience": int(input("Enter years of experience: "))
    }

    return candidate

    The interesting part wasn't the syntax.

    It was the design decision.

    Instead of creating variables outside the function and depending on them later, the function became self-contained. It now owns one complete responsibility—collect candidate information and return a structured object.

    That might seem like a small improvement, but this principle appears everywhere in backend engineering.

    Whether it's a recruitment platform, an ATS, or any business application, well-designed functions are easier to reuse, test, and maintain.

    Another small reminder from today's revision:

    Phone numbers are identifiers, not numbers.

    Although they contain digits, they shouldn't usually be stored as integers because we don't perform mathematical operations on them, and leading zeros may be significant.

    🧠 ML Revision

    Today's revision was on Precision.

    Accuracy tells us how often a model is correct overall.

    Precision answers a different question:

    Out of all the candidates the model shortlisted, how many were actually good candidates?

    For AI-powered recruitment systems, improving precision means recruiters spend less time reviewing unsuitable profiles.

    Revisiting fundamentals has been surprisingly valuable. Every small refinement today becomes a stronger foundation for building larger systems tomorrow.

    Restart Day 8/90
    Understanding What Really Happens After You Click "Submit"
    Most of us use websites every day.
    We fill forms.
    We click Submit.
    The page updates.
    But I never really stopped to think about what actually happens between those two clicks.
    Today's learning was about HTTP Requests and HTTP Responses, and one simple analogy made it click for me.
    Imagine you're recharging a mobile number.
    You fill in:

    {
    "provider": "Jio",
    "amount": 250,
    "state": "Telangana"
    }

    When you press Recharge, this information travels from the frontend to the backend.
    That message is called an HTTP Request.
    The backend then validates the request, processes the recharge, and sends a message back:

    {
    "status": "Recharge Successful"
    }

    This message coming back is called an HTTP Response.
    The same pattern exists in almost every application we use today.
    Whether you're:
    applying for a job
    ordering food
    booking a cab
    shopping online
    the flow is almost always:
    User
    ↓
    Frontend
    ↓
    HTTP Request
    ↓
    Backend
    ↓
    Business Logic
    ↓
    Database
    ↓
    HTTP Response
    ↓
    Frontend
    ↓
    User

    Understanding this flow made me realize something important:
    Frameworks like FastAPI don't create magic.
    They simply receive HTTP requests, execute Python code, and send HTTP responses.
    🧠 ML Concept of the Day
    Regression is a machine learning task where the output is a number instead of a category.
    Examples:
    Predicting a candidate's expected salary
    Predicting a candidate score
    Predicting house prices
    💡 Today's Takeaway
    Learning a framework is useful.
    Understanding how data travels through an application is what makes you a backend engineer.

    Restart Day 7/90 – Understanding How Frontend and Backend Actually Talk
    One thing I realized today is that backend development starts making much more sense once you understand what actually happens after a user clicks the Submit button.
    Let's take a simple example.
    Imagine a candidate applies for a job by filling out a form:
    Name: Vaibhav
    Experience: 3 Years
    Skill: Python
    When the candidate clicks Submit, this is what happens behind the scenes:
    Candidate
    ↓
    Frontend (Website)
    ↓
    HTTP Request (JSON)
    ↓
    FastAPI Backend
    ↓
    Business Logic
    ↓
    Database
    ↓
    HTTP Response
    ↓
    Frontend
    ↓
    "Application Submitted Successfully"
    The frontend is responsible for collecting the user's input and sending it as a JSON request.
    The backend receives that request, validates the data, runs the business logic (for example calculating a candidate score or calling an AI model), stores the information in a database, and finally sends a response back to the frontend.
    One small realization today:
    Frameworks like FastAPI are much easier to understand once the flow of communication between the frontend and backend is clear. Learning the framework is only one part of backend engineering—understanding how data travels through a system is equally important.
    🧠 ML Concept of the Day: Inference
    After a model has finished learning from training data, using it to make predictions on completely new data is called Inference.
    Example:
    A trained resume-screening model receives a new resume.
    It predicts Shortlisted or Rejected.
    That prediction process is inference.
    💡 Today's Takeaway:
    Every application—whether it's a recruiter platform, an e-commerce website, or a banking app—follows the same fundamental flow:
    User → Frontend → Backend → Database → Response → User
    Understanding this flow is helping me connect Python fundamentals with real backend development and AI automation systems.
